# Plan: Sub-module structure for `mod_data_select`

**Date:** 2026-07-02  
**Goal:** Introduce three picker sub-modules under `mod_data_select`, with data flowing upward through to `mod_data_analysis`.

---

## 1. Overview of the pattern

In golem/Shiny, data is passed **upward** from a child module to its parent by having the child module server function **return a reactive**. The parent module captures that reactive as a local variable, and can then react to it or pass it further up. This is the recommended pattern.

```
mod_map_picker_server(...)        → returns reactive (selected datasets from map)
mod_aggregated_picker_server(...) → returns reactive (selected datasets from table)
mod_user_upload_server(...)       → returns reactive (selected datasets from upload)
         ↓ (all three captured by parent)
mod_data_select_server(...)       → combines all three → returns reactive (all selected datasets)
         ↓ (captured in app_server)
mod_data_analysis_server(..., datasets = selected_data)  → consumes data for analysis
```

---

## 2. Shared data structure

Each sub-module returns a **`reactive`** that evaluates to a **named list of dataset objects**. Each element of that list represents one selected dataset and should follow a consistent structure, for example:

```r
list(
  list(
    id       = "ReSCUE_2021_BTO_North_Sea",   # unique identifier
    source   = "map",                          # "map", "table", or "upload"
    meta     = list(species = "Puffin", ...),  # metadata tibble row / named list
    data     = <tibble>                        # the actual flight-height data
  ),
  ...
)
```

When a sub-module has no items selected, it returns an empty list `list()`.

The parent (`mod_data_select`) merges the three lists with `c()` and returns the combined reactive.

## 4. Sub-module structure (template)

Each sub-module server returns a reactive:

```r
mod_map_picker_server <- function(id) {
  moduleServer(id, function(input, output, session) {
    ns <- session$ns

    # Internal reactive state tracking what this picker has selected
    selected <- reactiveVal(list())

    # ... UI logic to add/remove datasets from `selected` ...

    # Return the reactive upward — the parent will call this like a function
    return(reactive(selected()))
  })
}
```

The `return()` at the end is key. The **parent captures it** as:

```r
map_selection      <- mod_map_picker_server("map_picker")
table_selection    <- mod_aggregated_picker_server("aggregated_picker")
upload_selection   <- mod_user_upload_server("user_upload")
```

## 5. Changes to `mod_data_select.R`

### UI
- Replace the current inline tab content with calls to each sub-module's UI function:
  - `bslib::nav_panel("Map Selection", mod_map_picker_ui(ns("map_picker")))`
  - `bslib::nav_panel("Table Selection", mod_aggregated_picker_ui(ns("aggregated_picker")))`
  - `bslib::nav_panel("Data Upload", mod_user_upload_ui(ns("user_upload")))`
- The "Selected Data" and "Flight Height Preview" cards on the right remain; they will reactively reflect `all_selected` (see below).

### Server
- Call all three sub-modules and capture their return values.
- Combine them into a single `all_selected` reactive using `reactive({ c(map_selection(), table_selection(), upload_selection()) })`.
- **Return `all_selected` upward** from `mod_data_select_server`.
- The "Selected Data" card and preview are driven by `all_selected`.

```r
mod_data_select_server <- function(id, nav_id = "main-nav", parent_session) {
  moduleServer(id, function(input, output, session) {
    ns <- session$ns

    # Call sub-modules and capture their reactive returns
    map_selection   <- mod_map_picker_server("map_picker")
    table_selection <- mod_aggregated_picker_server("aggregated_picker")
    upload_selection <- mod_user_upload_server("user_upload")

    # Merge all selections into one reactive
    all_selected <- reactive({
      c(map_selection(), table_selection(), upload_selection())
    })

    # Drive "Selected Data" summary card from all_selected
    # ... renderTable / renderUI using all_selected() ...

    # Navigate to Analysis tab
    observeEvent(input$go_analysis, {
      bslib::nav_select(id = nav_id, selected = "Analysis", session = parent_session)
    })

    # Return combined selection upward
    return(all_selected)
  })
}
```

## 9. Notes / open questions

- **What does each dataset object look like?** The `id`, `source`, `meta`, `data` structure above is a proposal. We should agree on this before implementing the individual pickers, as it drives how the data preview and analysis module consume data.
- **Skeleton vs. full implementation?** The three new picker modules can start as functional skeletons (returning placeholder/dummy reactives in the correct structure) so the data-threading wiring can be tested end-to-end before building out each picker's full UI.
- **`mod_source_filter`** appears in the architecture diagram as a sub-module of `mod_data_select` that communicates bidirectionally with `mod_map_picker`. This is not planned here but should be noted for a future step — it would sit inside `mod_data_select` and pass filter parameters down into `mod_map_picker`.
